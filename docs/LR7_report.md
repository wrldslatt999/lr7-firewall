# Звіт з лабораторної роботи №7

**Тема:** Розробка програмного брандмауера.  
**Виконав:** Чучула Євгеній Андрійович.  
**Мета:** реалізація власного програмного модуля фільтрації мережевих підключень, керування правилами, журналювання відмов і детектування конфліктів.

## 1. Сервіс фільтрації з динамічними правилами

Реалізовано навчальний застосунковий брандмауер за моделлю TCP/UDP-проксі з додатка викладача. Він керує двома окремими типами мережевих запитів: новими TCP-з'єднаннями і кожною UDP-датаграмою на визначених портах. Режими `in` та `out` застосовуються відповідно перед прийняттям потоку й перед його пересиланням на конфігурований кінцевий сервер. Системні пакети поза цими портами не перехоплюються.

Застосовано `RuleManager` із синхронізацією `RLock`. Для кожного правила перевіряються IPv4/CIDR, порт (1–65535; значення 0 є шаблоном у правилах), TCP/UDP, напрям, `allow/deny`, `enabled`, пріоритет. Результат визначається за першою відповідністю в порядку `priority ASC, deny before allow, id ASC`. За відсутності збігу діє базова політика `allow` з локальної конфігурації; оператор може встановити `deny` перед запуском.

Інтерфейс керування доступний тільки на `127.0.0.1:18081` та вимагає секретного заголовка `X-Admin-Token`. `fwctl.py` здійснює `list`, `add`, `enable`, `disable`, `delete`, `reload`, `conflicts`, `evaluate`. Зміни застосовуються **до нових підключень і датаграм відразу**, без рестарту проксі та з атомарним збереженням до `config.json`. Уже встановлені TCP-сеанси продовжують працювати за попереднім рішенням — це свідоме обмеження архітектури.

## 2. Журналювання й аналіз

Застосовано JSON Lines (`logs/events.jsonl`) з UTC-часом у ISO8601. Події `connection.denied` та `datagram.denied` містять `src_ip`, `src_port`, `dst_ip`, `dst_port`, `protocol`, `direction`, `rule_id`, `reason`. Події `rule.added`, `rule.updated`, `rule.deleted` відображають зміну політики, `admin.denied` — невдалі спроби доступу до API. Навмисно не зберігаються корисний вміст пакетів або секретний токен.

Скрипт `analyze_logs.py` підтримує фільтри `--action`, `--proto`, `--direction`, `--src`, `--dst`, `--since`, `--until`, а також створює статистику відхилень за протоколом, напрямом, причиною та IP.

В одному фактичному запуску в локальному Linux-середовищі підготовки проєкту (не Kali) зафіксовано **18 подій**, серед яких **3 відмови** (2 TCP, 1 UDP). Це результати конкретного автоматизованого сценарію `tools.run_demo`, а не статистика реальної мережі. Кількість і характеристики подій у Kali залежать від повторення тестів.

## 3. Правила у реальному часі й конфлікти

Оператор може додавати й відключати правила під час роботи служби через API. Дублікат, повністю тотожний уже наявному правилу, повертає `409`. Якщо новий запис перекривається за CIDR і портами з активним записом того ж протоколу та напряму, система повідомляє про конфлікт різних дій (`conflict`) або дублювання зони дії (`overlap_same_action`). Операції залишаються детермінованими завдяки пріоритету й політиці `deny` при однаковому значенні пріоритету. Формальну перевірку коректності CIDR здійснено через модуль `ipaddress`.

У локальному інтеграційному сценарії підтверджено послідовність: **TCP дозволений → правило ввімкнено, TCP відхилений → правило вимкнено, TCP дозволений → знову ввімкнено, TCP відхилений**, а також блокування UDP у напрямі `out`. Перезапуск між змінами не виконувався.

## Перевірки працездатності

- Виконано `43` модульні й інтеграційні тести на локальному Linux-середовищі; результат `OK`.
- Реальні TCP/UDP сокети з локальним echo-сервером, не лише симуляція рішення.
- Перевірені TCP/UDP `allow`, `deny`, вхідний і вихідний напрям, зміна правил на льоту.
- Перевірено відмову при відсутньому токені Admin API (`401`), дублікаті (`409`), некоректних портах та IP (`400`).
- Дані перевірок з Kali Linux додаються після повторного виконання у файлі `docs/kali-demo.json`.

## Висновки та можливі вдосконалення

Завдання щодо фільтрації через проксі, динамічного керування правилами, журналювання відмов, пошуку в логах та виявлення конфліктів реалізовано в навчальному обсязі. Проксі **не підміняє системний брандмауер**: він не бачить з'єднань повз налаштовані порти, не підтримує IPv6, ICMP, повноцінний state tracking, глибинний аналіз або захист від DoS. Для виробничого середовища необхідна інтеграція з `nftables`/Netfilter або іншим системним механізмом фільтрації, сильніша авторизація адміністратора з аудитом дій і обмеженням швидкості, структуроване ротаційне зберігання логів та окремі політики для різних мережевих інтерфейсів.
